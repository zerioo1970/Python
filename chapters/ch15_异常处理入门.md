## 开篇：你的程序太脆了

到现在为止，你写的程序有个共同问题——**只要用户不按预期操作，立刻崩**。

```python
weight = float(input("体重："))      # 用户输一个字母 → 程序直接崩，什么都不剩
```

第 8 章我们靠 `isdigit()` 打了个补丁，第 14 章把它包成了函数，但那个方案有个根本缺陷：**你在替 Python 重新定义"什么是合法数字"**，而这件事你永远做不全（`3.5`、`-5`、`1e5`、`+5`、`1_000` 都是合法的）。

本章教一个完全不同的思路：

> **不预先判断，直接干；出错了再处理。**

这就是异常处理。学完之后你会发现，第 14 章那个越写越长的校验函数，**三行就能写完，而且支持全部合法写法**。

本章还有三处需要特别注意：

- **15.8 / 15.9 两条铁律**——裸 `except` 会让用户按不停你的程序，`except: pass` 会让 bug 彻底消失。这两个是**能造成真实事故**的写法
- **15.12 EAFP vs LBYL**——Python 和 C# / Java 习惯差别最大的地方，从那些语言转来的人一定会本能地写错
- **15.14 `assert` 的危险**——`python -O` 一跑，你的断言全部消失。我会用一个"透支成功"的演示让你记住

本章学完，**阶段一就结束了**，该动手做验收项目 A 了。

## 15.1 语法错误 vs 运行时异常

这两个词都叫"错误"，但**性质完全不同**，分不清就会白花时间。

**示例 15-1　两者的根本区别**

**语法错误：代码根本跑不起来，一行都不执行。**

```python
print("这一行看起来没问题")
if True                     # 少了冒号
    print("缺了冒号")
```

```text
  File "syntaxerr.py", line 2
    if True
           ^
SyntaxError: expected ':'
```

**注意第一行的 `print` 完全没有输出。** 因为 Python 要先把整个文件**编译**一遍，编译不通过就一个字节码都不执行。

**运行时异常：跑到那一行才崩，前面的代码已经执行完了。**

```python
print("第一行照样执行了")
n = int("abc")              # 跑到这里才崩
print("这一行永远到不了")
```

```text
第一行照样执行了
Traceback (most recent call last):
  File "crash.py", line 2, in <module>
    n = int("abc")
        ^^^^^^^^^^
ValueError: invalid literal for int() with base 10: 'abc'
```

**这次第一行输出了。** 这印证了第 2.9 节的观察。

**为什么必须分清？因为处理方式完全不同**：

| | 语法错误 | 运行时异常 |
|---|---|---|
| 什么时候发现 | **编译时**（还没开始跑） | **运行时**（跑到那一行） |
| 前面的代码 | 一行都不执行 | 已经执行完了 |
| 报错开头 | `File ...` + `SyntaxError` | **`Traceback (most recent call last):`** |
| 怎么解决 | **读代码改语法** | **可以用 `try` 处理** |
| 能被 `try` 接住吗 | **不能** | 能 |

最后一条值得实际验证一下——**`try` 接不住语法错误**：

```python
try:
    if True                 # 语法错误
        pass
except SyntaxError:
    print('接住了')
```

```text
  File "<string>", line 3
    if True
           ^
SyntaxError: expected ':'
```

`接住了` 没有打印——因为**整个文件都没编译成功**，`try` 那一行自己都没运行起来。

> **记住这条**：**看到 `Traceback` 开头就是运行时异常，本章的内容对它有用；看到 `SyntaxError` 就是打字错误，去改代码，别想着用 `try`。**

## 15.2 异常会一层层往上抛

**示例 15-2　异常的传播**

```python
def level3(x):
    return 10 / x

def level2(x):
    return level3(x)

def level1(x):
    return level2(x)

print(level1(0))
```

```text
Traceback (most recent call last):
  File "deep.py", line 10, in <module>
    print(level1(0))
          ^^^^^^^^^
  File "deep.py", line 8, in level1
    return level2(x)
           ^^^^^^^^^
  File "deep.py", line 5, in level2
    return level3(x)
           ^^^^^^^^^
  File "deep.py", line 2, in level3
    return 10 / x
           ~~~^~~
ZeroDivisionError: division by zero
```

**这就解释了第 2.10 节那个问题：Traceback 为什么是多行的。**

> **Traceback 的每一段，就是异常经过的一层函数调用。**

读法（第 2 章讲过，现在能真正理解了）：

| 位置 | 内容 | 怎么用 |
|---|---|---|
| **最后一行** | `ZeroDivisionError: division by zero` | **先看这个**——出了什么错 |
| **最下面那一段** | `line 2, in level3` | **出错的真正地点** |
| 中间各段 | `level1` → `level2` | 调用链，看它是怎么走到那里的 |
| 最上面那段 | `line 10, in <module>` | 最初的入口 |

`most recent call last` 就是"最近的调用在最后"——**所以最后那段才是案发现场**。

异常一路往上抛，**只要中途有人接住，程序就能继续**：

```python
def level3():
    return 1 / 0
def level2():
    return level3()
def level1():
    return level2()

try:
    level1()
except ZeroDivisionError as e:
    print("在最外层接住了:", e)      # => 在最外层接住了: division by zero
```

**没人接住，就一路抛到顶层，Python 打印 Traceback 并让程序退出**（退出码 1）。

## 15.3 `try` / `except` 最简形式

**示例 15-3　第一个 try / except**

```python
try:
    n = int("abc")          # 可能出错的代码放这里
except ValueError:          # 出了 ValueError 就执行这里
    print("转换失败")

print("程序继续跑")
# => 转换失败
# => 程序继续跑
```

**程序没崩。** 这就是异常处理的全部意义。

**有个关键认知**：`try` 里一旦出错，**剩下的语句直接跳过**，不会执行完。

```python
try:
    print("A")
    n = int("abc")          # 在这里出错
    print("B")              # 这一行【不会执行】
except ValueError:
    print("C")
# => A
# => C
```

`B` 没有打印。**这一点在写代码时必须心里有数**——不能指望 `try` 里的语句"部分成功"。

## 15.4 捕获特定异常

**示例 15-4　只捕获想管的那一种**

```python
try:
    n = int("abc")
except ValueError:              # 只管 ValueError
    print("接住了 ValueError")
# => 接住了 ValueError
```

**示例 15-5　捕获的类型不对，异常照样逃出去**

```python
try:
    n = int("abc")              # 抛的是 ValueError
except TypeError:               # 但你抓的是 TypeError
    print("这里抓不到")
# => ValueError: invalid literal for int() with base 10: 'abc'
```

**程序照样崩了。** `except` 只接住**匹配的**异常类型。

> **实用技巧**：**不确定会抛什么异常，就先让它崩一次，看清报错名再写 `except`。** 这比猜快得多。

**为什么要指定类型，不图省事全抓？** 因为**捕获范围越大，越容易把不该处理的错误也吃掉**：

```python
try:
    price = float(data["prcie"])    # 键名打错了 → KeyError（这是代码 bug）
except Exception:                   # 什么都抓
    print("数据格式有问题")           # ❌ 你以为是数据问题，其实是自己写错了键名
```

这个 bug 会被**永久掩盖**——程序不崩，只是每条数据都"格式有问题"。

**示例 15-6　一个 `except` 管多种**

```python
try:
    x = 1 / 0
except (ValueError, ZeroDivisionError):     # 注意要用【元组】，括号不能省
    print("一个 except 管多种")
# => 一个 except 管多种
```

括号不能省——写成 `except ValueError, TypeError:` 是 `SyntaxError`（那是 Python 2 的老写法）。

**示例 15-7　多个 `except` 分别处理**

**什么时候合并成一个、什么时候分开写？** 看**处理方式是否相同**：

```python
raw = "abc"

# ✅ 处理方式相同 → 合并成一个
try:
    value = float(raw)
except (ValueError, TypeError):
    value = 0
print(value)                    # => 0
```

```python
a, b = "10", "0"

# ✅ 处理方式不同 → 分开写，给不同的提示
try:
    result = int(a) / int(b)
    print(result)
except ValueError:
    print("请输入整数")
except ZeroDivisionError:
    print("除数不能为 0")         # => 除数不能为 0
```

**同一个 `try` 可以挂多个 `except`**，Python 从上往下找第一个匹配的——这就引出下一节要注意的顺序问题。

## 15.5 `except` 的顺序：具体的在前

**示例 15-8　顺序错了会静默失效**

```python
try:
    int("abc")
except Exception:               # ❌ 宽泛的写在前面
    print("宽泛的写在前面：这个先匹配上了")
except ValueError:              # 永远轮不到它
    print("具体的永远轮不到")
# => 宽泛的写在前面：这个先匹配上了
```

**注意：这不会报错，也不会警告。** 你精心写的 `except ValueError` 就是**永远不执行**，而你毫无察觉。

```python
try:
    int("abc")
except ValueError:              # ✅ 具体的在前
    print("具体的在前：正确")
except Exception:               # 兜底放最后
    print("兜底")
# => 具体的在前：正确
```

**原因**：`except` 是**从上往下依次匹配**的，第一个匹配上的就执行，后面的全部跳过。而 `ValueError` **是** `Exception` 的子类，所以 `except Exception` 一定会先抓到它。

> **记住这条**：**具体的异常写前面，宽泛的写后面。** `except Exception` 如果要写，永远放最后一个。

## 15.6 `except ... as e`：拿到错误信息

**示例 15-9　拿到错误信息给用户看**

```python
try:
    int("abc")
except ValueError as e:                 # as e 把异常对象绑到变量 e 上
    print("错误描述:", e)                # => 错误描述: invalid literal for int() with base 10: 'abc'
    print("异常类名:", type(e).__name__)  # => 异常类名: ValueError
    print("repr:", repr(e))             # => repr: ValueError("invalid literal for int() with base 10: 'abc'")
```

三种用法各有场合：

| 写法 | 得到 | 用在哪 |
|---|---|---|
| `str(e)` 或直接 `print(e)` | 错误描述文字 | 给用户看、写日志 |
| `type(e).__name__` | 异常类名（字符串） | 日志里记类型 |
| `repr(e)` | 类名 + 描述 | 调试时想看全 |

**注意 `KeyError` 的描述有点特殊**——它只给键名，还带引号：

```python
try:
    {"a": 1}["b"]
except KeyError as e:
    print("KeyError 的 e:", e)          # => KeyError 的 e: 'b'
    print("类名:", type(e).__name__)     # => 类名: KeyError
```

所以 `print(f"出错了：{e}")` 对 `KeyError` 会显示 `出错了：'b'`——**光看这个用户不知道发生了什么**。给用户的提示要自己组织文字：

```python
d = {"a": 1}
try:
    d["b"]
except KeyError as e:
    print(f"配置项 {e} 不存在，请检查配置文件")     # => 配置项 'b' 不存在，请检查配置文件
```

## 15.7 `else` 和 `finally`

### `else`：`try` 没出错才执行

**示例 15-10　else：成功了才做的事**

```python
def parse(s):
    try:
        n = int(s)
    except ValueError:
        return f"{s!r} 不是数字"
    else:                                   # try 里【没出错】才走这里
        return f"{s!r} 转成了 {n}，平方是 {n * n}"

print(parse("5"))       # => '5' 转成了 5，平方是 25
print(parse("abc"))     # => 'abc' 不是数字
```

**为什么不直接把 `n * n` 写在 `try` 里面？** 因为那样 `try` 块就变大了——如果 `n * n` 自己出了错，也会被 `except ValueError` 误抓。

**`else` 的价值就是让 `try` 保持最小**（15.13 会细说）。

### `finally`：无论如何都执行

**示例 15-11　finally 一定会执行**

```python
def f(x):
    try:
        r = 10 / x
        print("try 成功:", r)
    except ZeroDivisionError:
        print("except 处理了除零")
    finally:
        print("finally 一定执行")

f(2)
# => try 成功: 5.0
# => finally 一定执行

f(0)
# => except 处理了除零
# => finally 一定执行
```

**示例 15-12　连 `return` 都拦不住 `finally`**

```python
def g():
    try:
        return "从 try 返回"
    finally:
        print("即使 return 了，finally 还是执行")

print(g())
# => 即使 return 了，finally 还是执行
# => 从 try 返回
```

**注意输出顺序**：`finally` 先打印，然后函数才真的返回。

**`finally` 用来干什么？清理资源**——关文件、关数据库连接、释放锁。因为这些事**无论成功失败都必须做**。

**但有个陷阱：`finally` 里千万别写 `return`**：

```python
def h():
    try:
        return "try 的返回值"
    finally:
        return "finally 的返回值"      # ❌ 它会【覆盖】try 的返回值

print(h())      # => finally 的返回值
```

`try` 里那个 `return` 的结果被**悄悄丢掉了**。这种代码极难排查。

> **记住这条**：**`finally` 里只做清理，不写 `return`、不写 `break`。**
>
> **一个预告**：第 16 章的 `with` 语句就是 `finally` 的语法糖，专门用来关资源。学了 `with` 之后，你自己写 `finally` 的机会会少很多——但理解它是理解 `with` 的基础。

## 15.8 铁律一：不写裸 `except`

**这是本章第一条不能违反的规则。**

`except:` 后面不写类型，叫"裸 except"，它会捕获**一切**——包括那些**本来不该被捕获的东西**。

**先看异常的家族树**，这是理解本节的钥匙：

```python
print(KeyboardInterrupt.__mro__)
# => (<class 'KeyboardInterrupt'>, <class 'BaseException'>, <class 'object'>)
print(ValueError.__mro__)
# => (<class 'ValueError'>, <class 'Exception'>, <class 'BaseException'>, <class 'object'>)
```

画出来：

```text
BaseException                    ← 所有异常的祖宗
├── KeyboardInterrupt            ← 用户按了 Ctrl+C      【不是程序出错】
├── SystemExit                   ← 程序请求退出          【不是程序出错】
├── GeneratorExit
└── Exception                    ← 【真正的"程序出错"都在这一支】
    ├── ValueError
    ├── TypeError
    ├── KeyError
    ├── OSError ─── FileNotFoundError / PermissionError / IsADirectoryError
    └── ...
```

**关键点**：`KeyboardInterrupt` 和 `SystemExit` **不在 `Exception` 这一支下面**：

```python
print(issubclass(KeyboardInterrupt, Exception))      # => False    不是 Exception 的子类
print(issubclass(KeyboardInterrupt, BaseException))  # => True     但是 BaseException 的
print(issubclass(ValueError, Exception))             # => True
print(issubclass(SystemExit, Exception))             # => False
```

**这个设计是故意的**：按 `Ctrl+C` 和调用 `sys.exit()` **不是"程序出错"，是"外部要求退出"**，不该被错误处理代码吃掉。

**示例 15-13　裸 `except` 把 `Ctrl+C` 也吞了**

```python
# ❌ 裸 except 抓得住 KeyboardInterrupt
try:
    raise KeyboardInterrupt("模拟用户按下 Ctrl+C")
except:
    print("裸 except 把 Ctrl+C 也吞了 —— 用户按不停你的程序")
# => 裸 except 把 Ctrl+C 也吞了 —— 用户按不停你的程序
```

```python
# ✅ except Exception 抓不住它，Ctrl+C 能正常逃出去
try:
    try:
        raise KeyboardInterrupt("模拟用户按下 Ctrl+C")
    except Exception:
        print("这一行不会执行")
except KeyboardInterrupt:
    print("KeyboardInterrupt 顺利逃出去了 —— 程序能被停下")
# => KeyboardInterrupt 顺利逃出去了 —— 程序能被停下
```

**真实后果有多严重？** 把裸 `except` 放进一个循环里：

```python
import time

# ❌ 这个程序【按 Ctrl+C 停不下来】
while True:
    try:
        time.sleep(0.1)
    except:                     # Ctrl+C 产生的 KeyboardInterrupt 被这里吃掉了
        print("忽略了一个错误，继续跑")
```

我实测过：这个程序连按三次 `Ctrl+C` 都停不下来，最后只能用 `kill -9` 强杀（退出码 137）。而把 `except:` 改成 `except Exception:` 之后，一次 `Ctrl+C` 就正常退出了：

```text
Traceback (most recent call last):
  File "good.py", line 6, in <module>
    time.sleep(0.1)
KeyboardInterrupt
```

> **记住这条**：**永远不要写裸 `except:`，要兜底就写 `except Exception:`。**
>
> 这条规则没有例外。Ruff（第 37 章）有专门的规则 `E722` 会揪出裸 `except`。
>
> **为什么这个坑这么常见？** 因为裸 `except` 打字最少，而且在小脚本里"看起来能用"。它的害处只在**程序跑得久、用户想中断**时才暴露。

## 15.9 铁律二：不吞异常

**`except Exception: pass` 是最危险的三行代码。**

它的危害不是"程序崩了"，而是**程序不崩了，但结果悄悄是错的**。后者难查一百倍。

**示例 15-14　`except: pass` 让 bug 消失**

场景：算一批账单的总额。其中第三条数据的金额写成了 `"2,00"`（本意是 200，逗号敲错位置）。

```python
rows = ["100", "300", "2,00", "150"]

# ❌ 吞掉异常：什么都不说
total = 0
for r in rows:
    try:
        total += int(r)
    except Exception:
        pass

print(f"账单总额：{total} 元")        # => 账单总额：550 元
```

**`550` 这个数字看起来完全正常。** 它不是 0，不是负数，没有任何异样——**你永远不会发现少算了 200 元**。这张单子会一路流到财务那里。

```python
rows = ["100", "300", "2,00", "150"]

# ✅ 至少说一声
total = 0
bad = []
for r in rows:
    try:
        total += int(r)
    except ValueError:
        bad.append(r)
        print(f"⚠️  数据 {r!r} 无法解析，已跳过")

print(f"账单总额：{total} 元（跳过 {len(bad)} 条：{bad}）")
# => ⚠️  数据 '2,00' 无法解析，已跳过
# => 账单总额：550 元（跳过 1 条：['2,00']）
```

**总额还是 550，但现在你知道有问题了。** 这就是全部区别。

**最低要求**：

| 级别 | 写法 | 评价 |
|---|---|---|
| ❌ 绝对不行 | `except Exception: pass` | bug 彻底消失 |
| ⚠️ 最低要求 | `except Exception as e: print(f"出错: {e}")` | 至少留下痕迹 |
| ✅ 更好 | 记下是哪条数据、哪一行出的错 | 能定位 |
| ✅ 正式项目 | `logger.exception(...)`（第 21 章） | 带完整 Traceback，能存档 |

> **记住这条**：**`pass` 是异常处理里最危险的两个字。** 哪怕只是 `print`，也比什么都不做好一万倍。
>
> **什么时候 `pass` 才算正当？** 极少数情况：你**确实**不关心这个操作是否成功，而且**在注释里写明了原因**。例如"删除临时文件失败也没关系，反正系统重启会清"。**必须写注释解释为什么可以忽略**——否则下一个读代码的人（包括你）无法判断这是深思熟虑还是偷懒。

## 15.10 `raise`：主动抛出异常

**示例 15-15　主动抛出异常**

```python
def set_age(age):
    if age < 0:
        raise ValueError(f"年龄不能为负，收到 {age}")
    if age > 150:
        raise ValueError(f"年龄不合理，收到 {age}")
    return age

print(set_age(30))          # => 30

try:
    set_age(-5)
except ValueError as e:
    print("接住:", e)        # => 接住: 年龄不能为负，收到 -5
```

**什么时候该 `raise`？** 当函数遇到**无法继续下去**的情况时。

**为什么不返回一个错误值（比如 `None`）？** 因为**返回值会被忽略，异常不会**：

```python
def bad_set_age(age):
    if age < 0:
        return None             # ❌ 用返回值报告错误
    return age

result = bad_set_age(-5)
print("调用方很可能忘了检查:", result)      # => 调用方很可能忘了检查: None
```

调用方**没有任何强制**去检查这个 `None`。它会一路往下传，最后在某个毫不相关的地方炸掉一个 `TypeError`——那时你已经不知道源头在哪了。

**用异常，错误在源头就被喊出来了。** 这是它比返回错误码好的根本原因。

**`raise` 的消息要写清楚**：

```python
# ❌ 报错时不知道原因
raise ValueError()

# ⚠️ 知道是什么错，不知道具体值
raise ValueError("年龄不合法")

# ✅ 把实际收到的值也带上，排查时省一步
raise ValueError(f"年龄不能为负，收到 {age}")
```

**示例 15-16　处理一半，剩下交给上层**

`except` 里写一个**光秃秃的 `raise`**，表示"把当前异常原样再抛出去"：

```python
def load(name):
    try:
        return int(name)
    except ValueError:
        print(f"  [记录] 解析 {name!r} 失败，已登记")
        raise                       # 空 raise：记录完，异常继续往上抛

try:
    load("abc")
except ValueError as e:
    print("上层也知道了:", e)
# => 　[记录] 解析 'abc' 失败，已登记
# => 上层也知道了: invalid literal for int() with base 10: 'abc'
```

**这个模式很实用**：底层负责**记录**（它知道细节），上层负责**决定怎么办**（它知道业务）。两边都不越界。

> **注意**：空 `raise` 只能写在 `except` 块里面（它需要"当前异常"这个上下文）。
>
> `raise ... from ...`（保留原始原因的链式抛出）是第 22 章的内容。

## 15.11 异常不是流程控制

**示例 15-17　别用异常代替 `if`**

```python
lst = []

# ❌ 用异常判断列表是否为空
try:
    first = lst[0]
    print("第一个:", first)
except IndexError:
    print("列表是空的")
# => 列表是空的
```

```python
lst = []

# ✅ 用 if
if lst:
    print("第一个:", lst[0])
else:
    print("列表是空的")
# => 列表是空的
```

结果一样，但第二个版本**更短、更快、意图更明显**。

**判断标准就一句话**：

> **这个情况是"意料之外"，还是"日常分支"？**
>
> - **日常分支** → 用 `if`（列表可能是空的、用户可能没填某个字段）
> - **意料之外** → 用异常（用户输了字母、文件突然不见了、网络断了）

"列表是空的"是完全正常的一种情况，你**本来就打算判断它**——那就用 `if`。

## 15.12 EAFP vs LBYL：Python 的风格

**这是 Python 和 C# / Java 习惯差别最大的地方**，值得单独理解。

两种风格有正式的名字：

| 缩写 | 全称 | 意思 | 写法 |
|---|---|---|---|
| **LBYL** | Look Before You Leap | 先看清再跳 | `if 能行: 干` |
| **EAFP** | Easier to Ask Forgiveness than Permission | 请求原谅比请求许可容易 | `try: 干 except: 补救` |

**示例 15-18　两种风格对照**

先看字典取值，**两种都行**：

```python
scores = {"小明": 92}

# LBYL：先问"有没有"，再取
if "小红" in scores:
    print(scores["小红"])
else:
    print("没有小红的成绩")         # => 没有小红的成绩
```

```python
scores = {"小明": 92}

# EAFP：直接取，取不到再处理
try:
    print(scores["小红"])
except KeyError:
    print("没有小红的成绩")         # => 没有小红的成绩
```

**这个例子里 `if` 版甚至更清楚**——字典的键在不在，是个稳定的事实，不会在两行之间变化。

**但换成文件，差别就出来了。这是本节的重点。**

```python
import os

# ❌ LBYL 的隐患：检查和使用之间有个时间缝隙
if os.path.exists("data.txt"):
    # 就在这一瞬间，文件可能被别的程序删了、权限被改了、磁盘被拔了
    f = open("data.txt")        # 照样可能崩
```

而且 `os.path.exists()` **只回答了"存在吗"，没回答"我能打开吗"**。实测一下：

```python
import os

print(os.path.exists("/tmp"))       # => True        它确实存在
f = open("/tmp")
# => IsADirectoryError: [Errno 21] Is a directory: '/tmp'
```

**`exists()` 说 True，`open()` 照样失败**——因为它是个目录。同理还有：没有读权限、是个损坏的符号链接、是个特殊设备文件……**你不可能把所有情况都检查一遍**。

```python
# ✅ EAFP 没有这个缝隙：打开这个动作本身就是检查
try:
    f = open("data.txt")
except FileNotFoundError:
    print("文件不存在")
except PermissionError:             # 顺手把"存在但没权限"也处理了
    print("没有读取权限")
except IsADirectoryError:
    print("这是个目录，不是文件")
```

`open()` **一次性把所有问题都暴露出来**，而且每种都能分别处理。

**这一族异常有共同的父类 `OSError`**，不想分那么细就抓它：

```python
print(issubclass(FileNotFoundError, OSError))    # => True
print(issubclass(PermissionError, OSError))      # => True
print(issubclass(IsADirectoryError, OSError))    # => True
```

```python
import os

for path in ["不存在.txt", "/tmp"]:
    print(f"{path!r}: exists={os.path.exists(path)}", end="  ")
    try:
        open(path)
        print("open 成功")
    except OSError as e:                        # 一网打尽
        print(f"open 失败 -> {type(e).__name__}: {e}")
# => '不存在.txt': exists=False  open 失败 -> FileNotFoundError: [Errno 2] No such file or directory: '不存在.txt'
# => '/tmp': exists=True  open 失败 -> IsADirectoryError: [Errno 21] Is a directory: '/tmp'
```

**怎么选？给一张判断表**：

| 情况 | 推荐 | 理由 |
|---|---|---|
| 字典键、列表长度等**纯内存判断** | `if`（LBYL） | 状态不会突变，`if` 更直白 |
| **文件、网络、数据库等外部资源** | **`try`（EAFP）** | 检查和使用之间状态会变，且检查不全 |
| **类型转换**（`int()` / `float()`） | **`try`（EAFP）** | 规则复杂，别自己写检查 |
| 条件很便宜、失败很常见 | `if`（LBYL） | 异常的开销比 `if` 大 |
| 失败是罕见情况 | `try`（EAFP） | 正常路径上一行检查都不用做 |

> **记住这条**：**碰到外部资源（文件、网络）和类型转换，用 `try` 而不是先检查。**
>
> **给有 C# / Java 经验的读者**：那些语言里异常比较"贵"（要抓栈帧），所以习惯是尽量避免；**Python 里异常很轻量，用异常做错误处理是主流风格**，标准库自己就大量这么写——`int()` 就是靠抛异常来报告失败的，`dict[key]` 也是。
>
> 这不是"滥用异常"，这是 Python 的正常写法。**你从 C# 带来的"先检查"本能，在 Python 里往多数时候是负担。**

## 15.13 `try` 块要小

**示例 15-19　`try` 块塞太多东西**

```python
data = {"price": "abc", "count": "2"}

# ❌ 十行全包起来
try:
    price = float(data["price"])
    count = int(data["count"])
    subtotal = price * count
    discount = 0.9 if subtotal > 100 else 1.0
    total = subtotal * discount
    print(f"合计 {total}")
except ValueError:
    print("出错了 —— 但到底是 price 还是 count 出的错？不知道")
# => 出错了 —— 但到底是 price 还是 count 出的错？不知道
```

```python
data = {"price": "abc", "count": "2"}

# ✅ 只包可能出错的那一行，其余挪到 else
try:
    price = float(data["price"])
except ValueError:
    print(f"price 字段 {data['price']!r} 不是数字")      # 提示里带上具体字段和值
else:
    count = int(data["count"])
    subtotal = price * count
    discount = 0.9 if subtotal > 100 else 1.0
    print(f"合计 {subtotal * discount}")
# => price 字段 'abc' 不是数字
```

**大 `try` 还有个更严重的问题：会把无关的 bug 一起吞掉。**

```python
data = {"price": "10", "count": "2"}

# ❌ 大 try 把代码 bug 也吞了
try:
    price = float(data["price"])
    count = int(data["cnt"])            # 键名打错了，这是【代码 bug】
    print(price * count)
except Exception:
    print("以为是数据问题，其实是键名写错了 —— 被掩盖了")
# => 以为是数据问题，其实是键名写错了 —— 被掩盖了
```

```python
data = {"price": "10", "count": "2"}

# ✅ 小 try 让 bug 暴露出来
try:
    price = float(data["price"])
except ValueError:
    print("price 不是数字")
else:
    try:
        count = int(data["cnt"])
    except KeyError as e:
        print(f"KeyError: {e} —— 一眼看出是键名的问题")
# => KeyError: 'cnt' —— 一眼看出是键名的问题
```

> **记住这条**：**`try` 里只放真正可能出错的那一两行**，后续逻辑用 `else` 挪出去。
>
> 块越小，你越清楚是哪一行出的错，也越不容易误捕获。

## 15.14 `assert` 及其危险

**示例 15-20　`assert` 的用途**

```python
def calc_average(scores):
    assert len(scores) > 0, "scores 不能为空"    # 逗号后面是失败时的提示
    return sum(scores) / len(scores)

print(calc_average([90, 80]))       # => 85.0

calc_average([])
# => AssertionError: scores 不能为空
```

`assert 条件, 提示` 等价于"如果条件不成立，就抛 `AssertionError`"。

**它的正当用途只有一个**：检查"**按设计绝不该发生**"的内部状态，帮开发阶段尽早发现 bug。

### ⚠️ 危险：`python -O` 会把 `assert` 整体删掉

```python
def withdraw(balance, amount):
    assert amount <= balance, "余额不足"     # ❌ 绝不能这样做校验
    return balance - amount

print("正常调用:", withdraw(100, 30))
print("透支调用:", withdraw(100, 500))
```

正常运行：

```text
正常调用: 70
Traceback (most recent call last):
  ...
AssertionError: 余额不足
```

**加 `-O` 运行**（生产环境常这么干，为了略微提速）：

```text
正常调用: 70
透支调用: -400
```

**透支成功了，余额变成 -400。** 校验代码凭空消失，没有任何提示。

原因可以直接看到：

```python
print(__debug__)        # 正常运行 => True
# python3.12 -O 运行时 => False
```

`-O` 让 `__debug__` 变成 `False`，编译器就把所有 `assert` 语句**整个删掉**——不是"不执行"，是字节码里根本没有。

**所以规则很明确**：

| 用途 | 能用 `assert` 吗 |
|---|---|
| 检查"我的代码逻辑有没有写错"（内部不变量） | ✅ 可以 |
| 单元测试里的断言（第 29 章） | ✅ 可以（pytest 就靠它） |
| **用户输入校验** | ❌ **绝对不行** → `if` + `raise` |
| **权限检查** | ❌ **绝对不行**（这是安全漏洞） |
| **业务规则**（余额、库存、额度） | ❌ **绝对不行** |
| 外部数据的格式校验 | ❌ 不行 |

正确写法：

```python
def withdraw(balance, amount):
    if amount > balance:                            # 用 if
        raise ValueError(f"余额不足：余额 {balance}，取款 {amount}")   # 用 raise
    return balance - amount
```

> **记住这条**：**`assert` 是给开发者查自己 bug 用的，永远不要用它守护业务规则或安全边界。** 判断依据：**这个检查在生产环境消失了，会出事吗？** 会 → 用 `if` + `raise`。

## 15.15 常见异常速查

回收第 2.11 节那十个报错，这次补上**该怎么处理**这一列。下面每一行的报错文字都是实测的：

```python
int("abc")          # => ValueError: invalid literal for int() with base 10: 'abc'
{"a": 1}["b"]       # => KeyError: 'b'
[1, 2][9]           # => IndexError: list index out of range
1 / 0               # => ZeroDivisionError: division by zero
"a" + 1             # => TypeError: can only concatenate str (not "int") to str
undefined_name      # => NameError: name 'undefined_name' is not defined
"abc".push(1)       # => AttributeError: 'str' object has no attribute 'push'
open("无.txt")       # => FileNotFoundError: [Errno 2] No such file or directory: '无.txt'
```

| 异常 | 什么时候出现 | **该怎么办** |
|---|---|---|
| `ValueError` | 类型对但值不合法（`int("abc")`） | **捕获**，提示用户重输 |
| `KeyError` | 字典没这个键 | `d.get(k, 默认)`，或捕获 |
| `IndexError` | 序列越界 | 先判断 `len`，或捕获 |
| `ZeroDivisionError` | 除以 0 | 先 `if b == 0`，或捕获 |
| `FileNotFoundError` | 文件不存在 | **捕获**（第 16 章） |
| `PermissionError` | 没权限 | **捕获** |
| **`TypeError`** | 类型不对 | ⚠️ **通常是代码 bug，该改代码，不该捕获** |
| **`NameError`** | 名字不存在（多半是拼写错） | ⚠️ **改代码** |
| **`AttributeError`** | 对象没这个属性/方法 | ⚠️ **改代码** |
| `UnboundLocalError` | 局部变量未赋值（14.10） | ⚠️ **改代码** |

> **这张表最重要的是下面那三行。**
>
> **`TypeError` / `NameError` / `AttributeError` 几乎总是"你写错了"，不是"运行时意外"。** 用 `try` 把它们包起来，等于把自己的 bug 藏进地毯下面：
>
> ```python
> # ❌ 这样做等于永久掩盖一个拼写错误
> try:
>     result = data.appnd(x)          # 方法名拼错了
> except AttributeError:
>     pass
> ```
>
> **判断标准**：这个错误是**外部世界造成的**（用户输入、文件、网络），还是**我的代码写错了**？前者捕获，后者去改。

class InsufficientBalanceError(ValueError):

## 综合示例

### 示例 15-21　用 `try` 重写输入校验（兑现两次承诺）

第 8 章和第 14 章都留了同一句话："`isdigit` 挡不住负数和小数"。现在来兑现。

**先看 `isdigit` 版到底漏了多少**：

```python
for s in ["35", "-5", "3.5", "1e5", "+5", "1_000", "abc", ""]:
    print(f"{s!r:8} isdigit={s.isdigit()}")
```

```text
'35'     isdigit=True
'-5'     isdigit=False
'3.5'    isdigit=False
'1e5'    isdigit=False
'+5'     isdigit=False
'1_000'  isdigit=False
'abc'    isdigit=False
''       isdigit=False
```

**只有第一个通过。** 而 `-5`、`3.5`、`1e5`、`+5`、`1_000` **全都是合法的 Python 数字**，却被判为非法。

想支持它们，用 `isdigit` 就得开始打补丁：去掉负号再判断、数一数几个小数点、小数点不能在开头也不能在结尾、处理 `e`、处理下划线……**越写越长，而且总有漏的**（这正是第 12 章 `rstrip(".csv")` 那个教训的重演——**自己重新实现语言已有的规则，几乎必错**）。

**换个思路：不预先判断，直接交给 Python 转，转不成它会告诉我们。**

```python
for s in ["35", "-5", "3.5", "1e5", "+5", "1_000"]:
    print(f"{s!r:8} float={float(s)}")
```

```text
'35'     float=35.0
'-5'     float=-5.0
'3.5'    float=3.5
'1e5'    float=100000.0
'+5'     float=5.0
'1_000'  float=1000.0
```

**六种写法全部支持，一行代码都没写。** 而真正非法的会抛 `ValueError`：

```python
for s in ["abc", "", "3.5.1"]:
    try:
        float(s)
    except ValueError as e:
        print(f"{s!r:8} -> ValueError: {e}")
# => 'abc'    -> ValueError: could not convert string to float: 'abc'
# => ''       -> ValueError: could not convert string to float: ''
# => '3.5.1'  -> ValueError: could not convert string to float: '3.5.1'
```

完整的输入循环：

```python
while True:
    raw = input("请输入体重（公斤）：").strip()

    try:
        weight = float(raw)          # 直接转，成不成让 float 自己说
    except ValueError:               # 转不成会抛 ValueError，正好接住
        print("请输入一个数字，例如 65 或 65.5")
        continue                     # 重新问

    if weight <= 0:                  # 格式对了，再查业务规则（日常分支，用 if）
        print("体重必须大于 0")
        continue

    break

print(f"记录体重：{weight} 公斤")
```

实际运行：

```text
请输入体重（公斤）：abc
请输入一个数字，例如 65 或 65.5
请输入体重（公斤）：-5
体重必须大于 0
请输入体重（公斤）：65.5
记录体重：65.5 公斤
```

**两个版本对照**：

| | `isdigit` 版 | `try` 版 |
|---|---|---|
| 小数 `3.5` | ❌ 要打补丁 | ✅ 天然支持 |
| 负数 `-5` | ❌ 要打补丁 | ✅ 天然支持 |
| `1e5` / `+5` / `1_000` | ❌ 几乎不可能覆盖全 | ✅ 天然支持 |
| 代码行数 | 越写越多 | **固定三行** |
| 谁定义"什么是合法数字" | 你自己（**容易漏**） | Python 的 `float()`（**权威且完整**） |

**注意这段代码的一个设计**——格式校验用 `try`，业务规则用 `if`：

- "用户输了字母" 是**意料之外**的输入错误 → 用异常
- "体重是负数" 是**预期内**的一种情况，你本来就要判断 → 用 `if`

这就是 15.11 那条"异常不是流程控制"的实际应用。

> **记住这条**：**要判断"这段文本能不能转成 X"，不要自己写规则，直接 `try` 转一下。** 判断日期、判断 JSON 是否合法，都是这个套路。

### 示例 15-22　安全转换工具函数

把上面的思路包成工具函数，全程序复用：

```python
def to_int(text, default=0):
    """把文本转成整数，转不成就返回 default。

    参数：
        text: 待转换的内容，可以是任何类型
        default: 转换失败时返回什么
    返回：
        int 或 default
    """
    try:
        return int(text)
    except (ValueError, TypeError):     # ValueError: 值不对；TypeError: 类型不对（如 None）
        return default

for v in ["42", "abc", "", None, "3.5", 7, "  8  "]:
    print(f"{v!r:8} -> {to_int(v)}")
```

```text
'42'     -> 42
'abc'    -> 0
''       -> 0
None     -> 0
'3.5'    -> 0
7        -> 7
'  8  '  -> 8
```

**注意四个细节**：

1. **抓 `(ValueError, TypeError)` 两种**——`int("abc")` 抛 `ValueError`，`int(None)` 抛 `TypeError`。少抓一个就漏。
2. **`int("3.5")` 是失败的**（返回默认值 0），因为 `int()` 不接受小数点形式的字符串。要支持小数得用 `to_float`。
3. **`int("  8  ")` 成功**——`int()` 自己会去掉两边空白，不用你 `strip()`。
4. **`default` 参数**让调用方决定失败时怎么办：

```python
def to_int(text, default=0):
    try:
        return int(text)
    except (ValueError, TypeError):
        return default

print(to_int("abc", default=-1))        # => -1        用 -1 表示"无效"
```

浮点版同理：

```python
def to_float(text, default=None):
    """把文本转成浮点数，转不成就返回 default（默认 None，表示"没有值"）。"""
    try:
        return float(text)
    except (ValueError, TypeError):
        return default

print(to_float("3.5"))                  # => 3.5
print(to_float("abc"))                  # => None
print(to_float("abc", default=0.0))     # => 0.0
```

> **`default=None` 还是 `default=0`？** 看语义：**`None` 表示"没有值"，`0` 是一个真实的值。** 处理"这一格没填"的数据时，用 `None` 更诚实——否则你分不清"用户填了 0"和"用户没填"。

### 示例 15-23　健壮的成绩录入程序

**验收项目 A3 的最终形态。** 函数（第 14 章）+ 循环（第 8 章）+ 字典（第 11 章）+ 异常（本章）全部用上。

```python
def ask_float(prompt, min_value=None, max_value=None):
    """反复询问直到用户输入一个合法的数字。min/max 为 None 时不检查该侧。"""
    while True:
        raw = input(prompt).strip()
        try:
            value = float(raw)
        except ValueError:
            print("  请输入一个数字")
            continue
        # 用 is not None：因为 min_value=0 是合法的（0 是 Falsy！见 14.6）
        if min_value is not None and value < min_value:
            print(f"  不能小于 {min_value}")
            continue
        if max_value is not None and value > max_value:
            print(f"  不能大于 {max_value}")
            continue
        return value            # 用 return 直接结束函数，比 break 更干净


def add_student(students):
    """录入一个学生的成绩存进 students。返回 False 表示用户想结束了。"""
    name = input("姓名（直接回车结束录入）：").strip()
    if not name:                        # 提前返回（14.13）
        return False
    scores = {}
    for subject in ["数学", "语文"]:
        scores[subject] = ask_float(f"  {subject}成绩：", min_value=0, max_value=100)
    students[name] = scores
    return True


def report(students):
    """打印成绩报表，按总分从高到低。"""
    if not students:
        print("没有任何数据")
        return
    print()
    print("姓名 | 数学 | 语文 | 平均")
    print("-" * 28)
    # key 用 lambda 取"两科之和"（14.14 的一瞥用法）
    for name, scores in sorted(students.items(),
                               key=lambda kv: sum(kv[1].values()),
                               reverse=True):
        avg = sum(scores.values()) / len(scores)
        print(f"{name} | {scores['数学']:>4.0f} | {scores['语文']:>4.0f} | {avg:>5.1f}")
    print("-" * 28)
    print(f"共 {len(students)} 人")


students = {}
while add_student(students):        # 一直录入，直到用户直接回车
    pass
report(students)
```

### 五个必须注意的差异

**① 观念上最大的差异：Python 里异常很便宜，鼓励用。**

C# / Java 里抛异常要抓栈帧，代价明显，所以你学到的是"异常用于异常情况，正常流程别用异常"。**Python 里异常是轻量的，而且标准库本身就用异常报告普通失败**——`int("abc")` 抛异常、`dict[key]` 抛异常、迭代结束抛 `StopIteration`。

所以 C# 里的 `int.TryParse` 那种"用返回值报告失败"的模式，**Python 里没有对应物，也不需要**：

```python
# ✅ 这就是 Python 的 TryParse
def try_parse(s):
    try:
        return True, int(s)
    except ValueError:
        return False, 0
```

**你从 C# 带来的"先检查再动手"（LBYL）本能，在 Python 里多数时候是负担**——尤其是文件和网络操作，见 15.12。

**② `except Exception` 不等于 `catch (Exception)`。**

C# 的 `Exception` 是（几乎）所有异常的根。Python 的根是 **`BaseException`**，`Exception` 只是它下面的一支：

```text
BaseException
├── KeyboardInterrupt      ← Ctrl+C，【不在 Exception 之下】
├── SystemExit             ← sys.exit()，【不在 Exception 之下】
└── Exception              ← 真正的"程序出错"
```

**这个设计是 Python 的优点**：写 `except Exception` 时，你自动不会吞掉用户的中断请求。而 C# 里 `catch (Exception)` 会连 `OperationCanceledException` 一起抓，得手工排除。

**推论：Python 里千万别写 `except BaseException`**，那才等于 C# 那个坏习惯。

**③ Python 有 `else` 子句，C# 没有。**

```python
try:
    conn = connect()
except OSError:
    print("连不上")
else:
    use(conn)           # 只有连上了才执行
```

C# 里你得在 `try` 里加个标志变量，或者把 `use(conn)` 也放进 `try`（那就扩大了捕获范围）。**`else` 是 Python 特有的好东西，用它保持 `try` 最小。**

**④ `assert` 和 `Debug.Assert` 的相似之处是"都会在发布时消失"，但触发条件不同。**

C# 的 `Debug.Assert` 在 Release 构建下消失；Python 的 `assert` 在 **`python -O`** 运行时消失。区别是：**Python 的"发布"默认不带 `-O`**，所以你的 `assert` 通常还在——这反而更危险，因为你可能从没见过它消失，直到某天运维加了 `-O`。

**结论一样**：绝不用它们做业务校验。

**⑤ 没有 checked exception（Java 特有）。**

Java 强迫你 `throws IOException` 或者当场处理。**Python 完全不强迫**——任何函数都可能抛任何异常，签名里看不出来。

**代价**：你必须靠 docstring 写清"什么情况会抛什么"（14.11 说过），或者靠读文档、读源码。**这是 Python 的一个真实缺点**，别指望编译器帮你。

### 一个 SQL 背景的类比

`try/except/else/finally` 和事务的结构很像：

| SQL | Python |
|---|---|
| `BEGIN TRAN` | `try:` |
| `ROLLBACK` + 错误处理 | `except:` |
| `COMMIT`（一切正常才提交） | **`else:`** |
| 无论如何都要释放连接 | `finally:` |

而 15.9 那条"不吞异常"，对应的正是**你绝不会写的那种 `BEGIN TRY ... BEGIN CATCH ... END CATCH`（catch 块里什么都不做）**——那样事务失败了却当成成功，数据就静默错了。**同一个道理。**

## 本章易错点

| ❌ 情况 | 症状 | ✅ 解法 | 原因 |
|---|---|---|---|
| **裸 `except:`** | 连 `Ctrl+C` 都被吞，程序停不下来 | **`except Exception:`** | 裸 except 捕获 `BaseException` |
| `except BaseException` | 同上 | 同上 | 同上 |
| **`except Exception: pass`** | 出错无声无息，**数据悄悄错了** | 至少 `print(e)` | 吞掉了错误信息 |
| `except Exception` 写在最前面 | 后面的 `except` **永远不执行，且不报错** | 具体的在前，宽泛的在后 | 从上往下依次匹配 |
| 捕获的异常类型不对 | 异常照样逃出去 | 先跑一次看清报的是什么 | `except` 只接匹配的 |
| `except ValueError, TypeError:` | `SyntaxError` | `except (ValueError, TypeError):` | 多种异常要用元组 |
| **`try` 块包了十几行** | 不知道哪一行出的错；无关 bug 被吞 | 只包一两行 + 用 `else` | 粒度太粗 |
| 用 `except IndexError` 判断列表空 | 逻辑绕、更慢 | `if lst:` | 异常不是流程控制 |
| **捕获 `TypeError`/`NameError`/`AttributeError`** | 自己的 bug 被永久掩盖 | **去改代码** | 它们是代码 bug，不是意外 |
| **用 `assert` 做输入/权限/业务校验** | `python -O` 运行时**校验全部消失** | `if` + `raise ValueError(...)` | `-O` 会删除所有 assert |
| `raise ValueError()` 不带消息 | 排查时不知道原因和实际值 | `raise ValueError(f"...收到 {x}")` | 消息是给排查的人看的 |
| **`finally` 里写 `return`** | 覆盖 `try` 的返回值，行为诡异 | `finally` 里只做清理 | 执行顺序陷阱 |
| `if os.path.exists()` 后再 `open` | 中间状态可能变；且 exists 不代表能打开 | 直接 `try: open(...)` | 检查与使用之间有缝隙 |
| 以为 `exists()` 为真就能打开 | `IsADirectoryError` / `PermissionError` | 捕获 `OSError` | exists 只答"存在吗" |
| 用返回 `None` 报告错误 | 调用方忘了检查，错误传到别处才炸 | `raise` | 返回值会被忽略，异常不会 |
| 想用 `try` 接住 `SyntaxError` | 接不住，整个文件都没编译 | 去改语法 | 语法错误在编译期 |
| `to_int` 只抓 `ValueError` | `to_int(None)` 崩掉 | 抓 `(ValueError, TypeError)` | `int(None)` 抛 TypeError |
| 空 `raise` 写在 `except` 外面 | `RuntimeError: No active exception` | 只在 `except` 块里用 | 它需要"当前异常" |

## 本章小结

### 基础

- **语法错误**：编译期发现，**一行都不执行**，`try` 接不住 → 去改代码
- **运行时异常**：跑到那一行才崩，前面已执行完，**可以用 `try` 处理**
- 看报错开头就能分辨：`Traceback` = 运行时异常，`SyntaxError` = 打字错误
- 异常**一层层往上抛**——这就是 Traceback 为什么多行；**最下面那段是案发现场**
- `try` 里一旦出错，**剩下的语句直接跳过**

### 四个子句

| 子句 | 什么时候执行 |
|---|---|
| `try` | 放可能出错的代码，**越小越好** |
| `except` | 出了匹配的异常时 |
| `else` | **`try` 没出错**时（用它把 `try` 缩小） |
| `finally` | **无论如何**（含 `return` 之后）——只做清理，**别写 `return`** |

- `except (A, B):` 一并处理多种；**具体的写前面，`except Exception` 永远放最后**
- `except ... as e`：`str(e)` 看描述、`type(e).__name__` 看类名
- 不确定抛什么异常，**先让它崩一次看清报错名**

### 两条铁律

1. **永远不写裸 `except:`，要兜底就 `except Exception:`**
   - `KeyboardInterrupt` 和 `SystemExit` **不在 `Exception` 之下**，这是故意的设计
   - 裸 `except` 会让用户**按不停你的程序**（实测要 `kill -9`）
2. **永远不写 `except Exception: pass`**
   - 危害不是"崩了"，是**"不崩了但结果悄悄是错的"**——难查一百倍
   - 最低要求：`print(e)`；正式项目用 `logger.exception`（第 21 章）
   - 真要忽略，**必须写注释说明为什么可以忽略**

### `raise`

- `raise ValueError(f"...，收到 {x}")`——**消息里带上实际值**
- **用异常报错好过返回 `None`**：返回值会被忽略，异常不会
- `except` 里写光秃秃的 `raise` = 原样再抛出去（**底层记录，上层决定**）

### 判断与风格

- **异常不是流程控制**：**日常分支用 `if`，意料之外用异常**
- **EAFP（先干，出错再说）是 Python 的主流风格**，尤其对：
  - **外部资源**（文件、网络、数据库）——检查和使用之间状态会变，而且 `exists()` 不代表能打开
  - **类型转换**——规则复杂，别自己重新定义
  - 纯内存判断（字典键在不在）用 `if` 更清楚
- **`try` 块要小**：只放真正可能出错的一两行，其余用 `else` 挪出去
- **`TypeError` / `NameError` / `AttributeError` 通常是代码 bug，该改代码，不该捕获**

### `assert`

- 只用于检查"**按设计绝不该发生**"的内部状态，以及单元测试
- ⚠️ **`python -O` 会把 `assert` 整体删除**（实测：透支校验消失，余额变成 -400）
- **绝不能用它做**：用户输入校验、权限检查、业务规则
- 判断依据：**这个检查在生产环境消失了会出事吗？** 会 → `if` + `raise`

### 本章最实用的一招

> **要判断"这段文本能不能转成数字/日期/JSON"，不要自己写规则，直接 `try` 转一下。**
>
> `isdigit` 版挡不住 `-5`、`3.5`、`1e5`、`+5`、`1_000`（全是合法数字）；
> `try: float(s)` 版**三行代码全部支持**，因为"什么是合法数字"由 Python 定义，不由你定义。
